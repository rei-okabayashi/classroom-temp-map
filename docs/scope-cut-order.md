# 完成が危ういときに削る順序

「9/4の完成デモに間に合わなさそうだ」と感じたとき、その場で相談しながら決めるのではなく、**あらかじめ決めておいた順番どおりに機能を削って完成を守る**ための資料です。

## なぜ先に決めておくのか

完成間際の焦っているタイミングで「何を削るか」をゼロから話し合うと、時間もかかるうえに、声の大きい意見に流されやすくなります。あらかじめ順番を固定しておけば、その場では「今どの段まで削ったか」を確認するだけで済み、判断に迷いません。

削る基準はひとつだけです。**製作した機器はメンバー全員分そのまま残します。「1人1台」の担当と、プロジェクト終了後の譲渡の約束（README参照）は、規模を削る場合でも変わりません。**

## 削る順序（4段固定）

完成が危ういと判断したら、次の順番で規模を縮めます。上の段から着手し、それでも間に合いそうなら途中で止めてかまいません。

1. **拡張候補（[docs/backlog.md](backlog.md) の項目）は全部やらない**
   前倒しで着手していた拡張機能があっても、ここで打ち切ります。
2. **発表グラフを1種類に絞る**
   校内発表（[docs/presentation-outline.md](presentation-outline.md)）で見せるグラフの種類を減らします。
3. **常設記録の日数を短縮する**
   教室に常設して記録する期間を短くします。
4. **設置点を4→3カ所に減らす**
   測定する場所を1か所減らします。**製作した機器は全員分そのまま残し、誰の担当機も取り上げません。**

## 判断のタイミング

- **8/28（金）**：中間デモ②。この時点でも規模を見直す判断はできますが、主な判断日は次の9/2です。
- **9/2（水）ごろ**：完成できるかどうかの見込みチェック。ここで危ないと判断したら、上記の順序で削り始めます。
- **9/4（金）**：完成デモ＋KPT（ふりかえり）。
- それでも間に合わない場合の最終手段が**延長**です。延長は最大1週間まで（〜9/11）、かつ1回限りです。延長する場合は、金曜デモの場でチームに宣言し、翌登校日に先生へ発表日の確認を取ります。

## 決め方

- 削る／延長するかどうかは、企画者が一人で決めるのではなく、**チームで進捗を確認したうえで企画者がまとめます**。
- 遅れが出ていること自体は責めません。まずタスクの切り方を疑い、本人と一緒に小さく分解し直すのが基本の考え方です（[README](../README.md) の週次リズム参照）。規模を削るのは、分解し直しても間に合わない見通しが立ったときの手段です。
- 「順調なフリ」が一番危険です。危ういと感じたら、金曜デモの場で状況ごと共有してください。
