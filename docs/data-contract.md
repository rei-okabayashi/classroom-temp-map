# データ契約 v1 — 教室の温度ムラ「見える化」

- 状態：**企画者承認済み・v1確定（2026-08-10）→ Day 0（8/17）でメンバーに説明・承認**
- これは「ノード ⇄ 集約M5Stack」の**約束事**。ここさえ揃っていれば、4人が並列で作っても最後に必ず合流できる。
- **「v1」の v はバージョン（版番号）のこと。** 資料の「第1版・第2版」と同じで、いまは第1版なので v1。**ルールを変えたいときは、必ずチームで合意してから版番号を1つ上げる**（v1→v2。勝手に項目を足さない）。こうすると、新旧のルールが混ざっても「どの版で作られたデータか」を区別できる。

## 1. 全体のルール

| 項目 | 決め | つまりこういうこと |
|---|---|---|
| 送信周期 | **30秒に1回** | 各ノードは電源が入ってから30秒おきに測って送る。ノードどうしで送るタイミングを合わせる必要はない |
| 通信方式 | ESP-NOW **ユニキャスト** | ESP-NOW＝WiFiルーターなしでESP32どうしが直接データを飛ばせる無線のしくみ。ユニキャスト＝「その場の全員に向かって叫ぶ」のではなく、**宛先を1台決めて送る**方式。宛先は集約役のM5Stack |
| 宛先の指定 | M5Stackが起動画面に自分のMACアドレスを表示 → 各自が `config.h` に書き写す | MACアドレス＝機器1台ごとに工場出荷時から付いている固有の番号（**機器の住所**のようなもの）。`config.h`＝各ノードのプログラムの中にある設定ファイル。書き写しはDay 0にやる |
| チャンネル | **1に固定** | チャンネル＝無線の通り道の番号（トランシーバーの「チャンネルを合わせる」と同じ）。送る側と受ける側が同じ番号になっていないと届かない |
| 暗号化 | なし | 暗号化＝通信の中身を他人に読めなくする処理。ここを流れるのは温度と湿度だけで個人情報がないので、設定が簡単な「なし」を選ぶ |
| 送信失敗時 | 「届いたよ」の返事がなければ**1秒後に1回だけ再送**。それでもダメなら諦めて次の周期に任せる | しつこく再送しないのは、30秒後にはどうせ次の測定データが来るから。1回分くらい欠けても分析には響かない（欠けたこと自体は下の `seq` で分かる） |
| 時刻 | **ノードは時計を持たない**。データが届いた瞬間に、M5Stackが自分の時計で時刻を付ける | 時計を持つのは集約M5Stackの1台だけ。ノード4台の時計をぜんぶ合わせる手間をなくすための決め |

## 2. 送る中身（ノード → 集約）

データは **JSON（ジェイソン）** という書き方で送る。JSONは「`項目名:値`」をカンマで並べる、機械が読み間違えないための書き方。見た目は暗号っぽいが、読み方は簡単。

正常時に送るのはこの1行：

```json
{"v":1,"id":"n1","seq":123,"t":26.4,"h":55.2}
```

日本語にすると——**「契約の版は1。私はノードn1。これは起動してから123回目の送信。気温26.4℃、湿度55.2%」**。

センサーの読み取りに失敗したときは、気温・湿度の代わりに `err` を入れて送る：

```json
{"v":1,"id":"n1","seq":124,"err":"sensor"}
```

日本語にすると——**「契約の版は1。私はノードn1。124回目の送信。センサーの読み取りに失敗した」**。

### 各項目の意味

| 項目名 | 入る値 | いつ入れる | 意味 |
|---|---|---|---|
| `v` | 整数（いまは必ず `1`） | 毎回 | この契約の**版番号（バージョン）**。受け取る側はこの数字で「どの版のルールで作られたデータか」を見分ける。ルール変更でv2になったら、更新前のノードのデータ（`v:1`）が混ざっても区別できる |
| `id` | 文字（`"n1"`〜`"n4"`） | 毎回 | **ノードの名前**。どのノード（＝どの場所）の測定かを表す。各ノードの `config.h` に固定で書き込む。名前と設置場所の対応表はREADMEで管理 |
| `seq` | 整数（0から+1ずつ） | 毎回 | **通し番号**。送信のたびに1ずつ増える。受け取った側で番号が飛んでいたら（例：123の次が125）「途中の1回が電波の途中で消えた」と分かる。ノードを再起動すると0に戻ってよい |
| `t` | 数値（小数1桁） | 正常時のみ | **気温（℃）**。センサーSHT31が返した生の値をそのまま送る（ズレの補正は集約側の仕事。ノードでは何もしない） |
| `h` | 数値（小数1桁） | 正常時のみ | **湿度（%）** |
| `err` | 文字 | 失敗時のみ | `"sensor"`＝センサー読み取り失敗の印。**失敗しても黙らずに送る**のがポイントで、「何も送ってこない＝ノードごと止まっている」と「errを送ってくる＝ノードは生きていてセンサーだけ故障」を見分けられる（生存報告を兼ねる） |

- **この6個以外の項目を勝手に足さない**。足したくなったらチームで合意 → 版番号を上げる（v1→v2）。
- 1回分のデータは約60バイト。ESP-NOWが一度に送れる上限（250バイト）の1/4以下なので余裕は十分。

## 3. 集約側の記録（SDカード・CSV）

- CSV＝**カンマ区切りの表形式ファイル**。Excelやスプレッドシートでそのまま開ける。
- ファイルはSDカードの `/LOG.CSV`。**1件受け取るたびに1行追記して、その場でSDカードへの書き込みを確定させる**（＝突然電源が切れても、消えるのは最大1行だけ）。
- **CSVには生の値を記録する**。校正オフセット（＝基準の温度計と並べて測ったときのズレの補正値。8/25の校正作業で決める）は別管理とし、**画面表示にだけ適用**している（記録した生データを後から汚さないため）。分析のときにも補正を掛けるかどうかは**未決定**——8/25の校正より前にチームで決める（論点は docs/backlog.md 項目4）。

列の並び：`recv_time,clock,node_id,seq,temp_c,hum_pct,status`

| 列 | 意味 |
|---|---|
| `recv_time` | M5Stackがそのデータを**受け取った時刻**（例 `2026-08-21 10:30:15`） |
| `clock` | `set`／`unset`。M5Stackの時計が**設定済みかどうかの印**。`unset` の間の `recv_time` は仮の時刻なので、分析のときは除外するか後で手補正する |
| `node_id` `seq` `temp_c` `hum_pct` | 送られてきた中身の書き写し（`err` のときは `temp_c` `hum_pct` を空欄にする） |
| `status` | `ok`＝正常／`sensor_err`＝センサー読み取り失敗 |

例（2行目がセンサー失敗の例）：

```csv
2026-08-21 10:30:15,set,n1,123,26.4,55.2,ok
2026-08-21 10:30:22,set,n3,98,,,sensor_err
```
