## 1. しきい値超過アラート（M5Stack画面の色変化）

- **目的**：気温・湿度が設定した範囲を超えたときに、数値を読まなくても一目でわかるようにします（現状は数値表示のみです）。
- **やること**：
  - 閾値をコード上の定数（または集約側の設定）として持たせます。集約とは、4台のノードからデータを受け取ってまとめる係のM5Stackのことです。
  - 各ノード（ノード＝教室に置く測定係の小さなコンピューター。ESP32＋温湿度センサーのセット。n1〜n4の4台）の最新値が閾値を超えたら、そのノードの表示部分の背景色または文字色を変えます。閾値内に戻ったら通常色に戻します。
- **受入基準（完成の定義）**：任意のノードの気温または湿度が設定した閾値を超えたとき、M5Stack（画面つきの小型マイコン。教壇に置いて受信データを表示・記録します）画面の該当ノードの表示色が変わります。閾値を下回れば元の色に戻ります。閾値はコードを書き換えれば変更できます。
- **ついでの小改善候補**：フッタの `drop:N`（＝取りこぼした受信の件数表示）表示は件数が極端に増えると右隣の `SD OK/NG`（＝SDカードへの記録が正常かどうかの表示）表示と重なるため、画面まわりを触るときに `999+` で頭打ちにします（999件を超えたら「999+」とまとめて表示する、という意味です。急ぎではありません）。
- **目安工数**：半日〜1日（表示処理の追加のみ）。
- **前提・注意**：データ契約（v1）の変更は不要です。表示だけの機能なので、CSV（カンマ区切りの表形式ファイル。Excelやスプレッドシートでそのまま開けます）の記録内容には影響しません。閾値の具体的な数値（何℃・何%か）は、常設記録で実際に出ている値の範囲を見てからチームで決めます。

## 2. 不快指数（WBGT近似）の算出・表示

- **目的**：気温・湿度の数値だけでなく、「体感的にどれくらい暑いか」を一つの指標で見せます。
- **やること**：
  - 気温・湿度から不快指数（DI）またはWBGTの近似式（気温・湿度のみを使う簡易式）を、集約（ゲートウェイ）側のM5Stackで計算します。
  - 計算結果を画面に追加表示します。
- **受入基準（完成の定義）**：画面に各ノードの不快指数（またはWBGT近似値）が表示されます。使った計算式とその出典（何の近似かの説明）を、コードのコメントかREADMEに明記してあります。
- **目安工数**：半日（既存の公開されている簡易式を使う想定です。新規の計算式を考案するわけではありません）。
- **前提・注意**：ここでいう「WBGT近似」は、黒球温度・気流を使う正式なWBGTではなく、気温・湿度だけから推定する簡易式であることを、表示またはドキュメントに明記してください（誤解防止のためです）。この値をCSVにも残したい場合は、データ契約のv2化（フィールド追加）が必要です。チーム合意が前提となります。表示だけなら契約変更は不要です。

## 3. M5Stackに時系列ミニグラフ（直近1時間）

- **目的**：数値の一覧だけでなく、「上がっているか下がっているか」という傾向を画面で見えるようにします。
- **やること**：
  - 直近1時間分のデータ（30秒周期なら1ノードあたり最大120点）を、M5Stackのメモリ上に保持します。
  - M5GFX（M5Stack用の画面描画ライブラリ）で簡易な折れ線グラフを描画します。全ノード同時表示が見づらければ、ノードを切り替えて表示する方式にします。
- **受入基準（完成の定義）**：画面上に、直近1時間の気温（または湿度）の推移が折れ線グラフとして表示されます。M5Stackの再起動でグラフの中身が消えるのは仕様として許容します（SDカードの過去ログを読み直してグラフ化するのは対象外、と明記しておきます）。
- **目安工数**：1〜2日（データ保持・グラフ描画・軸のスケーリングの実装）。
- **前提・注意**：M5Stack Basicは画面サイズ・メモリに制約があるため、複数ノードを1画面に重ねて描くと見づらくなりやすいです→ノードごとの切替表示が現実的です。M5Stackの時刻が未設定の間でもグラフ自体は「何周期前か」という相対軸で描けるので、時刻設定を前提にしなくても構いません。

## 4. CSV→SQLite/Pythonで時間帯×場所の集計・簡易ヒートマップ

- **目的**：SDカードに溜まったLOG.CSVを後から分析し、「いつ・どこの教室が暑いか」を見えるようにします（データ分析担当のロールで、訓練で習ったSQLite（ファイル1つで使える小さなデータベース）を活用します）。
- **やること**：
  - LOG.CSVを読み込んでSQLiteのテーブルに入れるスクリプトを作ります。
  - 時間帯（例：1時間ごと）×ノードID（＝設置場所）で気温・湿度の平均などを集計するSQL（＝データベースへの問い合わせに使う言葉）を書きます。
  - 集計結果をmatplotlib（グラフを描くためのPythonのライブラリ）等で簡易ヒートマップとして可視化します。
- **受入基準（完成の定義）**：LOG.CSVを入力として、SQLiteにデータが取り込まれ、時間帯×場所の平均気温（または湿度）がヒートマップ画像として出力できます。手順がREADME等に書いてあります（他のメンバーが再現できます）。
- **目安工数**：1〜2日。
- **前提・注意**：校正は実施しないことにしたため、補正の適用可否を判断する必要はありません。LOG.CSVの生値をそのまま集計します。`clock`列が`unset`の行（時刻未設定中に記録された行）は、分析から除外するか手動補正するか決めてから集計します（データ契約に既定があります）。

## 5. M5StackのAPモード＋スマホ閲覧

- **目的**：PCを開かなくても、スマホのブラウザから最新の状況を見られるようにします。
- **やること**：
  - M5StackをWiFiのAPモード（AP＝スマホなどがつなぎに行く、WiFiの親機の役割）で起動します。
  - 簡易なWebサーバーを立て、最新値（または直近のログ）をHTMLで返します。
- **受入基準（完成の定義）**：スマホをM5Stackが発するAPに接続し、ブラウザで指定URLを開くと、各ノードの最新値が表示されます。
- **目安工数**：1〜2日（ESP-NOW（WiFiルーターなしでESP32どうしが直接データを飛ばせる無線のしくみ）受信との共存検証を含みます）。
- **前提・注意**：**要検証**です。ESP32（無線通信ができる小型マイコン）はWiFi（APモード）とESP-NOWの受信を同じ無線チップ・同じチャンネル（無線の通り道の番号。トランシーバーの「チャンネルを合わせる」と同じです）で扱うため、同時利用にはチャンネルの制約があります（APのチャンネルをESP-NOW側のch1に合わせる必要があるなど）。着手前に「APモードを立てた状態でもESP-NOW受信が途切れないか」を実機で確認してください。両立が難しい場合は「配信中は受信を一時停止する」等の妥協案も検討します。

## 7. ノードのdeep sleep・電池運用

- **目的**：ノードをUSB給電ではなく電池で動かせるようにし、設置場所の自由度を上げます。
- **やること**：
  - ESP32のdeep sleep（一定時間だけマイコンを深く眠らせて消費電力を抑えるしくみ）を使い、30秒周期の送信の合間はスリープする構成に変更します（起床→センサー読み取り→送信→再スリープ）。
  - 電池（モバイルバッテリー等）での駆動時間を実測します。
- **受入基準（完成の定義）**：電池接続でノードが指定周期どおり送信を継続できます。deep sleep無し版との消費電流・駆動時間の比較データが残っています。
- **目安工数**：1〜2日（実装＋実測）。
- **前提・注意**：deep sleepから復帰するたびにWiFi/ESP-NOWの初期化が発生し、起動〜送信までの時間が伸びる点に注意してください。データ契約上、`seq`（通し番号。送信のたびに1ずつ増え、番号が飛んでいたら途中のデータが消えたと分かります）は再起動のたびに0に戻る仕様のため、毎周期deep sleepを挟む構成にすると`seq`の「パケットロス（＝送ったデータが途中で消えて届かないこと）検出」としての意味が薄れる可能性があります→運用上どう扱うかチームで合意してから着手してください。

## 9. 温度の妥当範囲チェック（異常値を弾く）

- **目的**：配線の接触不良やセンサー故障で「あり得ない温度」が返ってきたとき、それを正常な測定値として送ってしまわないようにします。現状の `readSensor()` はCRC（通信の途中でデータが化けていないかの検査）だけを見ていて、値そのものが妥当かは見ていません。
- **やること**：
  - `readSensor()` に温度（と湿度）の妥当範囲チェックを追加し、範囲外なら `false` を返します。
  - 妥当範囲として使う数値をチームで合意し、なぜその値にしたのかをコードのコメントに1行残します。
- **受入基準（完成の定義）**：範囲外の値を読んだときに `err` が送信され、集約側に `SENSOR ERR` と表示されることを、シリアルモニタで確認できます。使った範囲の根拠がコメントに書いてあります。
- **目安工数**：1時間。
- **前提・注意**：
  - **データ契約（v1）の変更は不要です。**ノード側の `loop()` には既に読み取り失敗用の送信経路（`err` を送る分岐）があり、`readSensor()` が `false` を返せばそのまま乗ります。集約側（`firmware/gateway/`）の変更も不要です。
  - 範囲の決め方は、センサー自体の測定範囲（−40〜125℃／0〜100%RH）より狭く取るほうが故障を早く見つけられます。広めの例は0〜60℃（明らかな故障だけを弾く）、狭めの例は5〜45℃（早く見つかるが真夏の締め切った教室で誤検知の可能性）。**常設記録の実測値を見て、実際に出ている範囲より少し広めに取るのが安全です。**
  - 他のノードへの展開は、1台で動いてから別途考えます。
  - 出どころは PR #46（mozu-sabo）の提案 → Issue #48。9/4の制作締切に間に合わないため、拡張バックログへ送りました（指摘自体は正しく、実際に穴になっている箇所です）。
