# 放課後の進め方 — 1時間の使い方と週ごとのゴール

- 対象：チーム全員です。8/17（月）のDay 0（チーム開発を始める初回の集まり）以降、放課後の時間をどう使うかの共通認識をつくるための資料です。
- チームの決めごと（README）とDay 0の進め方（docs/day0-agenda.md）を、実際の「時間割」に落としたものです。決めごと自体はDay 0で確認して確定します。

## 0. 前提（時間の制約）

- 授業は **15:05に終了**、**16:30に強制下校** です。教室に居られるのは最長85分ですが、**募集時にお伝えした「放課後45〜60分」の目安を守るため、16:10ごろまでに切り上げます**（作業に使えるのは45分＋動作確認10分が目安です。下校にも余裕ができます）。
- 放課後に集まるのは **週2〜3回** の想定です。**1週目だけは導入があるため月・火・金で確定**、2週目以降の曜日は、事前アンケートの「放課後に残れる見込みの日」の回答を見てDay 0で決めます（月曜と金曜は、下の「置き換え」の理由でなるべく集まりたい日です。8/18(火)に残れない人は個別フォローするので、事前に企画者へ伝えてください）。
- 放課後だけでは時間が足りないので、**自宅30〜60分×週2〜3回＋週末1〜3時間**と組み合わせます（合計は募集時にお伝えした「週5〜8時間」の範囲に収めます。この上限を超えないのもチームのルールです）。
- **8/27（木）は追加講習のため、放課後の作業はできません。** この日は集まらない前提で計画してあります（「2週目」参照）。

## 1. 放課後1回分の基本の型

| 時刻 | やること |
|---|---|
| 15:05〜15:10 | PCや機材の準備 |
| 15:10〜15:15 | 今日のゴールを1人ひとことずつ確認します |
| 15:15〜16:00 | 作業（詰まったら抱え込まず、その場で声をかけてペア作業にします） |
| 16:00〜16:10 | 動作確認＋「きょうやった／困ってる」の2行をDiscordに書きます |
| 16:10〜 | 片付け（機材を教室に置くか持ち帰るかの確認を含みます）→ 下校 |

曜日による置き換え：

- **月曜**：冒頭の作業時間15分を「週次キックオフ」に使います。今週の各自のタスクカード（Issue＝やることを1件ずつカードにしたもの）を確認します。カードの見かた・作り方は [docs/task-cards.md](task-cards.md) にまとめてあります。
- **金曜**：作業枠を「デモ」に置き換えます（8/21・8/28は中間デモ、9/4は完成デモ＋KPT。KPT＝ふりかえりの型で、Keep＝続けること・Problem＝困ったこと・Try＝次に試すことを出し合います）。
- **集まらない日**：作業は自宅の分だけでOKです。Discordの2行報告だけ忘れずにお願いします。

## 2. 週ごとの進め方と「週末ライン」

週末ライン＝その週の金曜が終わった時点で「ここまでできていれば順調」という目安です。届かなくても責めません（3章のルールで立て直します）。

### 1週目 8/17（月）〜8/21（金）：作る週

- この週は**月・火・金の3回**集まるのが基本です（導入とデモがあるためです）。
- 8/17（月）**Day 0**：役割の最終合意・機材配布・チームの決めごと確認。残り時間で学校PCへの導入（軽い分）を始めます（進め方は docs/day0-agenda.md）。
- 8/18（火）**学校PC導入デー**：Arduino IDE・esp32パッケージ・USBドライバなどの重い導入を終わらせます。**esp32パッケージのダウンロードは10〜30分かかるので、待っている間に Git演習（全員1周）を並行して進めます**（ダウンロードを仕掛ける → 待ち時間にGit演習 → 戻って続きを入れる、の順番です）。回線が混まないよう、ダウンロードを始めるタイミングは少しずつずらします。
- 平日：自分の担当ノード（教室に置く測定係の小さなコンピューター。ESP32＋温湿度センサーのセット）の製作を進めます。センサーの取り付け・配線・書き込みが中心です。
- 8/21（金）**中間デモ①**。
- **週末ライン**：全員の学校PCでコンパイル（プログラムを機械が実行できる形に変換して文法ミスがないか確かめること）が通っている＋**全員がGit演習のPRを1本マージ済み**＋**企画者機と最低1台のメンバー機のデータが、集約役のM5Stack（教壇に置く画面つきの小型マイコン）に届いている**。

### 2週目 8/24（月）〜8/28（金）：測る週

- 8/25（火）**全ノード稼働＋校正並走**（校正＝基準になる温度計と並べて測って、センサーごとのズレを調べることです）。
- 8/26（水）**教室に常設して記録開始**。ここから先は、電源が入っていれば夜間も自動で記録が続きます。
- 8/27（木）**追加講習のため放課後なし**。前日までに常設が始まっていれば、この日は何もしなくても記録は自動でたまります（自宅作業も任意です）。
- ※この週だけ、火・水にも教室での作業があります。8/25・8/26に残れるかどうかは、アンケートの回答をもとにDay 0で調整します。校正と設置は集約表示オーナー＋企画者が中心に進めるので、残れないノード担当は、**自分のノードを動く状態にして当日までに企画者へ預ければ大丈夫です**（この運用でよいかもDay 0で確認します）。
- 8/28（金）**中間デモ②**。
- **週末ライン**：4台全部が動いて常設記録が回っている＋**SDカードのCSV（カンマ区切りの表形式ファイル）をSQLite（ファイル1つで使える小さなデータベース。訓練校で学習済み）で読めている**。

### 3週目 8/31（月）〜9/4（金）：まとめる週

- 平日：たまったデータの分析・グラフ作成・発表準備を進めます。余裕があれば拡張バックログ（docs/backlog.md＝前倒しできたときに足す追加機能の一覧）に、そこに決めてある順番どおりに着手します。
- 9/2（水）ごろ：**完成できるかの見込みチェック**。危なければ、[規模を削る](scope-cut-order.md)か、完成期限を延ばす判断をします（延長は最大1週間・〜9/11まで。募集時にお伝えした条件です）。
- 9/4（金）**完成デモ＋KPT**。
- **週末ライン**：完成デモが通っている＋発表の骨子（docs/presentation-outline.md）に実データが入り始めている。

### 9/4のあと 〜 校内発表（9月中旬）：仕上げの期間

**9/4で制作は完成しますが、発表がまだ残っています。**この期間の見通しを先に書いておきます。

- **みなさんにお願いする作業は、この期間の合計で2〜3時間程度です**（募集のときにお伝えした「別途2〜3時間」がこれです）。中身はスライドの仕上げとリハーサル1回だけです。
- **リハーサルを1回だけやります。**発表日の2〜3日前に、実際の会場で機器を動かして通信できるかも確かめます（会場が普段の教室と違うと電波の状況が変わるためです）。
- 具体的な日程は、**9/4のふりかえり（KPT）の最後に、全員で4つ決めます**：①発表日が決まったら誰が連絡するか（企画者です）②リハーサルの候補日 ③当日の集合時間と役割（話す人・デモ操作・記録係）④この期間の作業量の確認。
- **教室に置いた機器の見守りは、9/4以降は企画者が引き取ります。**毎日の画面チェックは不要になります。
- 発表日そのものは9月中旬の予定で、**8/28（金）までに仮の日程を確定させます**（企画者が先生に確認します）。決まり次第Discordで共有します。

## 3. 遅れていると感じたら（READMEの決めごとの再掲。Day 0で確認して確定します）

- 詰まったら**24時間以内に申告**→企画者と30分のペア作業をします。遅れは責めません（タスクの切り方が悪かったとみなして、分解し直します）。
- 週末ラインに届かなかったときは、次の月曜キックオフで作戦を立て直します（1週目の遅れは2週目前半で吸収できる設計です）。
- 完成が危うくなったら、規模を削ります。何をどの順で削るかは [docs/scope-cut-order.md](scope-cut-order.md) に決めてあり、その場面になったらチームで確認します。
- 時間の上限は**週5〜8時間**です。**上限を超えてがんばらない**のもチームのルールです（無理は続かず、事故のもとになるためです）。
