## 0. 前提（この構成案が拠り所にしていること）

- チームは訓練校未経験メンバー中心＋企画者です。開発期間は8/17（Day 0）〜9/4（完成デモ+KPT。KPT＝ふりかえりの型で、Keep（続けること）・Problem（困ったこと）・Try（次に試すこと）の3つをまとめます）の約3週間です（進み具合により最大1週間の延長の可能性があり、〜9/11まで延びる場合があります）。
- 役割は、ノード担当（全員1人1台）、集約表示オーナー（メンバー1名）、データ分析、発表とりまとめ、筐体です。
  - ノードとは、教室に置く測定係の小さなコンピューターのことです。ESP32（無線通信ができる小型マイコン。マイコン＝プログラムで動く小さなコンピューター）＋温湿度センサーのセットで、n1〜n4の4台あります。
  - 集約とは、4台のノードからデータを受け取ってまとめる係のM5Stack（画面つきの小型マイコン。教壇に置いて受信データを表示・記録します）のことです。
  - データ分析にはSQLite（ファイル1つで使える小さなデータベース。訓練校で学習済み）を使います。
- データ契約（`docs/data-contract.md`）は、並列開発を支えた土台という位置づけです。
- 公開リポジトリ（リポジトリ＝プロジェクト一式の保管場所。フォルダごと、変更履歴つきで置いておく場所です）のため、学校名や教室が特定される情報はスライドにも書かないようにします（写真を使う場合は要チェックです）。

### 各セクションのメモ

**2. 課題（体感のばらつき）**
- 「同じ教室なのに席によって暑い/寒いと感じたことは？」という問いかけから入ると、聞き手を巻き込みやすくなります。
- ここではまだセンサーの数値は出しません。あくまで“体感”の話にとどめます。

**3. アプローチ（見える化）**
- 体感は人によってズレます。そこで、客観的な数値で複数地点を比較できるようにする、という一段だけの転換を明確に伝えます。
- 「なぜIoTで／なぜ自作なのか」に軽く触れておくと、4章の伏線になります。

**4. システム構成**
- ノードはESP32-DevKitC-32E＋AE-SHT31（温湿度センサー。SHT31＝温度と湿度を測るセンサー部品の型番です）を使います。30秒周期でESP-NOW（WiFiルーターなしでESP32どうしが直接データを飛ばせる無線のしくみです）でユニキャスト（その場の全員に向かって叫ぶのではなく、宛先を1台決めて送る方式です）送信します。
- 集約はM5Stack Basicです。受信してSDカードのCSV（カンマ区切りの表形式ファイル。Excelやスプレッドシートでそのまま開けます）に1行ずつ記録し、画面にも表示します。
- 「なぜESP-NOWか」はここで一言触れておくと、質疑の時間短縮になります（詳細は3章のQ&Aへ）。
- 図は`docs/`配下に既にある構成図があれば流用し、なければ発表とりまとめ担当が新規作成します。

**5. チーム開発の進め方**
- 未経験メンバーが1人1台のノードを並行して作れた理由は、データ契約（送信フォーマットを最初に固定したもの）とノード用の共通テンプレート（`firmware/node-template/`）です。
- Git運用は、feature branch（ブランチ＝本体（main）に影響を与えずに作業するための、枝分かれした作業用コピーです）→ PR（Pull Request＝「この変更を本体に取り込んでください」という提案です。チームの誰かが確認してから取り込みます）→ 企画者レビュー → マージ（提案された変更を本体に取り込むことです）という流れです。mainへの直接push（自分のPCでの記録をGitHub側に送って反映することです）はありません。
- AIルール4つをそのまま紹介します。
  1. 共通テンプレートを使う
  2. データ形式の契約を守る
  3. 説明できないコードはマージしない（PR説明欄に自分の言葉で書く）
  4. AIを使った箇所はREADMEに明記する
- 「軽量な進め方を選んだ理由」の言葉の骨子は、未経験者中心・実質3週間という制約の中で、重い計画駆動のプロセスより「先に約束事（データ契約・共通テンプレ）だけ固めて、あとは各自が短いサイクルでPRを出す」やり方の方が、詰まった時にすぐ軌道修正できるためです。金曜ごとの中間デモ（8/21・8/28）を合流ポイントとして挟んでいるのも同じ理由です。
- 【要確認】このセクションを「アジャイル」という言葉で説明するかどうかはチームで相談します（訓練内容と用語がリンクしているかどうかによります）。

**6. 運用データと分析**
- 「○日間」の日数は、実際の運用開始（8/26〜）から発表準備時点までの経過日数で確定します。【要確認】
- 時間帯×場所のクロス集計（例：朝/昼/放課後 × ノード設置地点）をグラフ1〜2枚で見せます。ヒートマップ的な見せ方が向いていそうです。
- 追加の校正（キャリブレーション＝基準になる温度計と並べて測ってセンサーごとのズレを調べること）は実施していません。SHT31が出荷時に校正済みであり、手元で用意できる温度計ではかえって精度を落とすためです（理由は想定問答3）。画面表示・CSV・分析のすべてが生値（センサーが返した値そのまま）で統一されています。
- なお、このプロジェクトで効いてくる誤差はセンサーの個体差（±0.2℃程度）よりも、**設置条件による差のほうが桁で大きい**です（基板の自己発熱・ケース内の熱こもり・日射・エアコンの吹き出し位置で1〜2℃）。聞かれたらこの順序で説明します。
- ノードの設置場所名は学校が特定されない表現にします（「窓際」「廊下側」など役割ベースの言い方に寄せます）。

**7. 改善提案**
- ここは実データが出てからでないと書けない枠です。プレースホルダとして「傾向A→提案A」の型だけ用意しておき、8/26以降の常設記録データが揃い次第、データ分析担当が中身を詰めます。
- 提案は必ず「このデータからこう読み取れる」という根拠とセットにします（感想ベースにしません）。

**8. 学び（KPT）**
- 9/4の完成デモ+KPTで出た内容をそのまま持ってくる想定です。今の時点では空欄です。

## 2. デモの段取り

### ライブデモ（うまくいく前提の手順）

1. 会場に集約M5Stackとノード最低1台を持ち込み、電源投入します。起動〜受信までの待ち時間をあらかじめ計っておきます。
2. 画面に気温・湿度・最終受信からの経過秒が表示される様子を見せます。
3. 可能ならその場でノードに軽く息を吹きかける、または手で覆うなどして数値が動く様子を見せ、「ちゃんとリアルタイムで反応している」ことを実感してもらいます。
4. SDカードを抜いてPCに挿し、`LOG.CSV`の中身をそのまま見せます（生データがある、という安心感を出します）。
5. 時間が許せば、データ分析担当のSQLite集計・グラフ画面を軽く見せます。

### リスクと対策

- 会場は普段の教室に確定し、機材も常設のまま使うので、会場での通信テストは不要です（当初は会場が違う場合にESP-NOWの電波状況を確かめる予定でした）。かわりに、授業終了から発表まで5分しかないため、**当日の準備は「確認」だけ**にします（docs/final-week-plan.md 5章）。
- 起動直後は最大30秒（1周期）表示が動かないので、「今データを待っています」と口頭でつなぎます。

### バックアップ運用（ライブが失敗した場合）

- 運用期間中（8/26以降）にM5Stackの画面や実際の動作を**事前に動画で撮影**しておきます（スマホでの手持ち撮影で可）。
- ライブデモが不通・機材トラブルの場合は、司会役が「今はこう動いています」と一言添えたうえで即座に録画へ切り替えます。切り替えの合図と担当者をチームで事前に決めておきます。
- スライドの該当ページに動画をあらかじめ埋め込む、またはすぐ再生できる状態にしておき、その場で探さないようにします。
- CSVの実データも、スクリーンショットをスライドに保険として仕込んでおきます（SDカードの抜き差しが会場で失敗しても止まらないようにするためです）。
- 【要確認】バックアップ動画の撮影担当・撮影日をチームで割り振ります。

## 3. 想定質問と答えの骨子

| # | 想定質問 | 答えの骨子 |
|---|---|---|
| 1 | なぜESP-NOW？ Wi-Fiじゃダメだったの？ | 学校のWi-Fiに接続する手間や制約がなく、宛先を固定したペアで直接やり取りできるためです。個人情報を含まない環境データなので、暗号化なしという単純な構成を選べました。 |
| 2 | 精度はどれくらい出るの？ | センサーはSHT31（秋月AE-SHT31）です。カタログ上の精度は、**温度が typ.（標準的な値として）±0.2℃、湿度が typ. ±2%RH** です（メーカーSensirionの製品ページ https://sensirion.com/products/catalog/SHT31-DIS-B より。測定範囲は −40〜125℃／0〜100%RH）。この ±0.2℃ は typ.（標準的な値）であって最大値ではない点に注意してください。SHT31は出荷時に個体ごとの校正が済んでいるため、追加の校正はしていません（理由は想定問答3）。 |
| 3 | 校正はしたの？ | **していません。実測して不要と判断しました。**まず実データで確かめました——誰もいない休日（空調停止・人の出入りなし）の5,741件で4台を突き合わせたところ、**台どうしの差は最大でも0.18℃**でした。これは今回見たい差（授業時間の平均1.9℃・最大4.3℃）の**10分の1以下**なので、補正を入れても結論は変わりません。背景として、SHT31は出荷時に個体ごとの校正が済んでいて、補正値がセンサー内部に書き込まれています（Sensirion公式データシート SHT3x-DIS（2022年12月・Version 7）の図1の説明文に *factory calibrated, linearized and compensated* と明記されています。https://sensirion.com/media/documents/213E6A3B/63A5A569/Datasheet_SHT3x_DIS.pdf ）。そのうえで校正し直すには、基準にする温度計のほうが**十分に正確**でなければ意味がありません。ところが市販の温度計はほとんどが ±1℃程度の製品で、typ. ±0.2℃のSHT31よりも粗いです。それを基準に補正すると、**基準器側の誤差をこちらに持ち込むだけ**になります。そのため記録・画面表示・分析のすべてを生値のまま統一しました。今回見たいのは「同じ時刻に教室のどこが暑いか」という**地点どうしの差**であり、4台とも同じ型のセンサーなので、絶対値のわずかなズレは結論を変えません。 |
| 4 | AIに書かせたの？ 自分で作ったと言えるの？ | AIは使いましたが、丸投げのコピペではありません。共通テンプレート・データ契約という土台を先に決め、各自が自分のPRで「なぜこの実装にしたか」を説明できることをマージ条件にしました。AI利用箇所はREADMEに明記しています。 |
| 5 | 費用はどれくらいかかった？ | 秋月での部材発注（8/1時点）が¥13,110、別途microSDが約¥1,000でした。合計で概算¥14,000程度です。【要確認：その後の追加購入があれば反映】 |
| 6 | データはどうやって分析したの？ | M5Stack側でSDカードにCSVをそのまま記録し、訓練で習ったSQLiteを使って集計・分析しています。生データと分析結果を分けて扱っています。 |
| 7 | 未経験のメンバーで3週間しかないのに、どうやって分担したの？ | 最初にノード⇔集約間の「データ契約」を固定し、共通テンプレートを用意したことで、各自が自分のノードを並行して作れる状態を作りました。8/21に中間デモで一度合流し、8/25に全ノード稼働のすり合わせをしています。 |
| 8 | 次に改良するなら何をする？ | 【要確認：チームで合意した上で埋める】想定される方向性としては、M5StackにRTC（電源を切っても時刻を覚えていられる時計の部品です）がなく、時刻を手動設定している点の解消、筐体の作り込み、ノード台数の拡張などです。 |

## 4. 発表資料作成の分担ルール

- **スライド本体（構成・文章・図の作成）は「発表とりまとめ」担当が作ります。** 企画者はスライド本体を作りません。
- 各セクションの中身は、担当ロールが情報を出す形にします。
  - システム構成（4章）→ ノード担当・集約表示オーナーが技術情報を提供します
  - チーム開発の進め方（5章）→ 全員の実体験＋企画者が事実確認のみ協力します
  - 運用データと分析／改善提案（6〜7章）→ データ分析担当が中身を作成します
- 企画者の関わりは**レビューのみ**です（事実確認、公開リポジトリとして問題ある記述のチェックなど）。文章そのものを書き直すことはしません。
- この文書（`docs/presentation-outline.md`）自体は構成の叩き台です。

### 何で作って、どこに置くか

- **スライドは Google スライドで作ります。** 全員がGoogleアカウントを持っていて（アンケートで使いました）、インストールが要らず、リンク1つで共有・共同編集できるためです。使い慣れたソフトが別にある場合は企画者に相談してください。
- 作ったら、**Discordの資料リンクのチャンネルに共有リンクを貼ります**（共有設定は「リンクを知っている全員が閲覧可」で十分です）。ファイルそのものはリポジトリには入れません。
- **構成図（4章）は、スライドソフトの図形機能で四角と矢印を並べれば十分です。**作図の専用ソフトは要りません。README.mdの先頭に図の元になる記述（Mermaid）がありますが、これは画像ではないので、見ながら描き起こす形になります。画像が必要なら企画者に言ってください。

### 各章の中身をいつまでに集めるか

スライドは1人では埋まりません。**他の担当に情報をもらう締切を、3週目の月曜キックオフで決めます。**目安は次のとおりです。

| 章 | 出す人 | 目安 |
|---|---|---|
| 4. システム構成 | ノード担当・集約表示オーナー | 3週目の火曜まで |
| 6〜7. 運用データと分析・改善提案 | データ分析担当 | 3週目の水曜まで |

受け渡しはDiscordの資料リンクのチャンネルで行います。締切を過ぎているものは、遠慮せず催促してください（催促は仕事のうちです）。
